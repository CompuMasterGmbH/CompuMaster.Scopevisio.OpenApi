# Complete product details

Issue #108 extends parent #17 and consuming CompuMasterGmbH/CompuMaster.Dms#90. Additive GetProductDetails exposes complete product JSON through synchronous, HTTP-info, asynchronous and native cancellable asynchronous forms. Historical GetProduct methods, result defaults, public signatures, caller token/account state and other product APIs remain unchanged.

GET /product/{id} uses the explicitly selected complete signed Int64 identifier with invariant text. Its current optional parameters are fields, formatValues and listExtended. Null values are omitted. Explicit empty/original fields and false/true options are retained independently. The documented formatting default is true and the extended-field option default is false; the client inserts neither default and never changes e-commerce settings.

The vendor ProductType schema lists available product fields. Its success description explicitly states that the effective field set can diverge with listExtended and the e-commerce extended-product-field setting. A true request is therefore not a guarantee that every schema field appears, and an omitted option is not inferred to mean a particular field set. Selected/future fields, formatted string values, false/null/empty metadata, the original externalModifieddTs spelling and all custom fields remain available in the complete JToken result. The existing ProductForm request model is not reused as a response contract. E-commerce SKUs remain available through their separate existing operation.

HTTP-info retains original raw JSON, status and response/content headers. Date-like/formatted strings are not interpreted or converted. Fractional JSON uses .NET decimal precision and can round or exceed its range; raw JSON remains exact. Missing product fields are not filled with zero, false, empty text or guessed account defaults.

The required profile is Produktverwaltung (Anzeigen). The current response table lists success without an exhaustive error-status list. The configured exception factory receives the original response before additive parsing and its exception instance is preserved. Server failures are not interpreted as local absence/permission/catalog decisions. Native cancellation reaches active HTTP I/O. No login, token renewal, account selection, formatting pass, lookup, retry or speculative mutation is added.

The audit uses the pinned 11 October contract, repository SHA-256 40060e2bbbf187b5d6f8a0397bc97a5e09e8c8cf5d548644d676b16e8f13c339. Three missing HTTP-info forms reproduce before implementation. Isolated fixtures exercise all six entry points, the independent omitted/false/true query combinations, bodyless GET, invariant signed identifiers, complete product/custom/future/formatted data, raw headers/status/errors, factory identity/order, pre/active cancellation and original legacy results. Actual field-selection/e-commerce/profile/formatting acceptance requires a separately coordinated account. Publication and downstream adoption remain separate.
