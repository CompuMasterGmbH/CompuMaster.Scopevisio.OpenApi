# Buffered invoice files and contact thumbnails

IncomingInvoiceApi.DownloadIncomingInvoiceFile, OutgoingInvoiceApi.DownloadOutgoingInvoiceFile and ContactApi.DownloadContactThumbnail expose original response bytes through synchronous, HTTP-info and native asynchronous forms. They cover the incoming invoice main file, outgoing invoice file and contact thumbnail GET routes. Historical generated void/Object methods and journal downloads remain unchanged.

Incoming invoices retain the original identifier or internal-number string. Outgoing file retrieval explicitly selects the original document number; the manufacturer calls the result the last file in its description and the main file in its response, so selection remains server-authoritative. Contact thumbnails use the original signed Int64 contact identifier without inferred minimums. Selectors are escaped without trimming, number conversion, lookup or state changes. Blank/relative invoice selectors are rejected. Requests have Accept */*, no body/query and the configured bearer/default headers.

The manufacturer supplies no fixed success MIME, filename, size or response schema. All 256 byte values are preserved without text/JSON conversion. Empty content remains an empty byte array; null remains possible if the existing transport supplies no bytes. HTTP-info retains status and combined response/content headers; RawJsonContent is null for binary data. The complete response is buffered in memory by the existing transport. These APIs do not deserialize a legacy file model, write temporary/destination files, generate invoices or update contacts. The caller owns any subsequent storage.

Profiles are Rechnungseingangsbuch (Anzeigen), Rechnungen (Anzeigen) and Kontakte (Anzeigen), respectively. A 404 can mean a missing resource, missing permission or missing file/thumbnail. Original server errors and the caller's exception factory remain authoritative; a disabled factory retains the original status and bytes. Cancellation reaches admission and active HTTP I/O without new speculative replay. Configuration, OAuth/token/account defaults and historical null-data behavior remain intact.

[SDK #118](https://github.com/CompuMasterGmbH/CompuMaster.Scopevisio.OpenApi/issues/118) tracks isolated .invalid byte/header/selection/error/cancellation fixtures, compiled compatibility and remaining coordinated actual file/thumbnail/profile verification. Builds and fake binary fixtures do not establish backend MIME/selection behavior, publication or downstream adoption.
