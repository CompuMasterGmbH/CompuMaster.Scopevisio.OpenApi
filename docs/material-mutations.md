# Explicit material inventory and purchase mutations

MaterialManagementApi is an additive API group, available directly with a Configuration or from OpenScopeApiClient.MaterialManagementApi. The facade initially shares its constructor configuration; callers can replace the group explicitly. Existing API groups, authentication/account-selection behavior, generated models and default configuration remain unchanged. The manufacturer groups these operations as BETA.

CreditMaterialInventory, CreateMaterialPurchaseDelivery, PostMaterialPurchaseDelivery and CreateMaterialPurchaseOrder expose the four documented POST routes with six sync/async/HTTP-info/native-cancellation forms each. Credit and delivery-post bodies are optional and null omits them; delivery/order creation bodies are required. Delivery posting requires an original selected master-ID/document-number string, escaped without trimming or numeric conversion; blanks/dot segments fail before HTTP. Supplied posting objects require postingDate.

Nine copied extensible models cover all input fields. MaterialInventoryCreditRequest/MaterialInventoryCreditRowRequest represent credit selections. MaterialPurchaseDeliveryCreationRequest/MaterialPurchaseDeliveryPostingRequest and MaterialPurchaseOrderCreationRequest preserve their distinct root choices. MaterialPurchasePartyRequest, MaterialPurchaseProductRequest, MaterialPurchaseUnitRequest and MaterialPurchasePositionRequest are shared because the order/delivery schemas have matching field shapes; their server resolution and candidate behavior remain distinct.

Inventory credit decreases product inventory and requires Bestandsverwaltung (Bearbeiten). Credit rows require an explicit product identity and quantity. The vendor required list names both productId and productNumber while their descriptions make them alternatives and give productId precedence if both are present. The SDK follows the explicit alternative/precedence prose: either known Int64 ID or original number is accepted, both remain unchanged, and absence of both fails. It does not fabricate the unused identity or reject a normal single-identity request solely to satisfy the contradictory required list. This explicit contract conflict remains a live clarification requirement.

Credit quantity has a declared minimum of zero. Original warehouseId omission retains the server's default warehouse. Deprecated contactId remains an explicit nullable input. Amount/price consistency, quantity multiplication and omitted price from a credited delivery remain server-authoritative; no local rounding, balancing or delivery-price lookup occurs. The server resolves available stock and original postingTs, project-driven dimension overrides and valid nonblocked dimension accounts. No product/warehouse/project/dimension/default timestamp is selected in the client.

Delivery/order creation requires vendor, original purchaseDeliveryDate/purchaseOrderDate and their position array. Each supplied position requires product, finite nonnegative quantity and finite nonnegative price; optional units remain unchanged. The schema defines no array minimum, so explicit empty arrays are sent unchanged while the server's HTTP 400 description requires at least one usable position. Actual vendor/product identification, product creation candidates and unit identity resolution remain server decisions. Original external-system/vendor/third-party IDs, leading-zero numbers, GTINs and unit names are not collapsed or prioritized locally.

All date schemas use yyyy-MM-dd patterns/examples while their prose also says dd.MM.yyyy. The SDK preserves original date strings without converting or guessing a format. Posting a delivery adjusts the requested date according to server business rules; the client does not infer the resulting date. Wareneingang (Bearbeiten) and Bestellung (Bearbeiten) profiles are enforced by the server.

Delivery enableAutomapping is explicit and omission retains server false. referencedPurchaseOrderNumbers preserves the complete original ordered string array. generatePurchaseOrderForRemainingValue requires automapping on the server; the client never turns it on implicitly, creates a follow-up order or merges order state. postDelivery is an explicit caller choice, with server posting-date requirements. Neither creation nor a returned HTTP 200 implies that posting occurred.

The server can create a genuine delivery/order or a candidate needing review. MaterialResponse declares status/results/feedback; results references a JSONArray object schema although actual result content is not fully described. ErrorRecord locationIdentifier declares object while examples use integers. The SDK keeps complete JToken results, future fields/severities and original feedback without coercing these inconsistencies, inferring a genuine versus candidate document, guessing affected counts or assuming transactionality. HTTP 200 callers inspect the actual result/feedback.

Source objects and nested JSON/arrays are deeply copied. Typed null setters omit fields, raw indexers preserve future fields and optional explicit JSON null, getters return defensive copies, and complete bodies snapshot before HTTP I/O. Known required fields, nested kinds and Int64 widths are checked. Finite numeric minimum-zero checks use the original number's mantissa, so negative tiny numbers cannot evade the minimum through decimal underflow; zero and positive tiny values remain unchanged. Optional signed amount/price values without a declared minimum are not clamped. Actual business validity remains server-enforced.

Complete raw JSON, HTTP status and response/content headers remain accessible. Configured exception-factory failures run before parsing. Empty response bodies have null data and unknown shapes remain available. Date-like strings stay strings; parsed fractions use bounded .NET decimal precision and may round or underflow, while raw JSON stays exact. No mutation retry, partial-failure replay or speculative follow-up is added. Native cancellation reaches HTTP I/O; cancellation after sending cannot establish what was applied.

Twelve absent-workflow cases fail before implementation. Isolated fake HTTP fixtures cover all forms, facade configuration, exact selections and date conflicts, credit identity alternatives, known required kinds/widths, minimum-zero/nonfinite/tiny values, snapshots, nested model copies, candidate feedback, complete errors/headers and active/pre-cancellation. No actual stock, order, delivery or server configuration is changed. Beta/live acceptance requires exclusive coordinated access, owned product/vendor/unit/inventory fixtures and verified restoration/cleanup. Full support, publication and downstream adoption remain deferred.
