# Incoming invoice responsible contact

`IncomingInvoiceApi.SetIncomingInvoiceResponsibleContact` adds PUT /incominginvoice/{idOrNumber}/responsiblecontact with six sync/async/HTTP-info/native cancellation forms. The invoice selection is the original required master-ID or number string. Leading zeros, Unicode, spaces and reserved characters are escaped without numeric parsing or trimming; blank and relative dot-segment selections are rejected before I/O.

`IncomingInvoiceResponsibleContactRequest` copies complete JSON and exposes optional Int64 ContactId. The manufacturer states that zero or negative contact IDs remove the attached user contact; these values are sent exactly only when selected by the caller. Typed null removes the request field, not the existing assignment. Unknown fields and explicit JSON null remain possible through the inherited object. The schema has no required properties and the body is optional: null request omits the body, an empty object stays empty and JSON-null contactId stays explicit. The SDK does not translate any omission/null into zero or automatically select removal; actual server handling of those original shapes remains authoritative.

The request snapshots before I/O and validates only the known optional Int64 JSON kind/width. No user lookup, contact-ID/range coercion, invoice/workflow fetch or automatic workflow repair occurs. The server enforces Rechnungseingangsbuch (Bearbeiten), valid user contacts and the detailed invoice/workflow prerequisites. The 404 descriptions include absent invoice/master/workflow/contact, workflow class/verification/state and completion conditions; an original 404 is not treated as proof of existence, permission or one specific failed condition. Original 500 assignment errors and custom exception factories remain unchanged.

Success declares HTTP 200 without a fixed result schema. Complete JToken/raw JSON/status/response+content headers are retained, including unknown/future content; an empty body has null data. No success count, assigned identity or actual workflow state is fabricated. Date-like result strings remain strings; parsed fractions use bounded .NET decimal precision and may round or underflow, while raw JSON remains exact.

Native cancellation reaches active HTTP I/O. Cancellation after sending cannot establish whether the assignment was changed. No new mutation retry or follow-up is added. Existing generated APIs/obsolete annotations/authorization/default behavior stay unchanged.

Isolated fake tests reproduce the absent workflow and cover all forms, exact assignment/removal IDs, optional/empty/null bodies, original escaped selections, copied snapshots, invalid known kinds/IDs, full results/headers/original 404/500/custom errors and pre/active cancellation. No actual invoice or contact is changed. Live contact/workflow/profile acceptance requires exclusive coordinated access and exact owned invoice restoration/cleanup; full support remains deferred. Publication and downstream adoption are separate.
