# Explicit organisation credential authorization

Configuration.OrganisationId is an optional Int64 selector for the high-level OpenScopeApiClient.AuthorizeWithUserCredentials and native AuthorizeWithUserCredentialsAsync methods. A specified ID is sent unchanged as organisation_id and takes precedence over OrganisationName; the name is omitted. No organisation catalog or display-name lookup, retry, default fallback or in-place organisation-change request is made. Null retains all existing default/name behavior, overload signatures and the single token request. Clear the ID to return to name/default authorization.

Use a separate client configuration for the intended organisation. The explicit-ID path stages the existing token request in an isolated configuration with the caller's HTTP client, base path, headers, timeout, user agent, date format and API exception factories. The returned bearer is used only by the staged fresh /myaccount read until validation succeeds. The token and account must explicitly contain the requested organisation ID as a JSON integer and agree on a nonblank Scopevisio UID; an omitted numeric field is not accepted as a zero-ID confirmation, and a fractional wire value must not be rounded into a matching integer. The previous active configuration bearer/client token remains intact on HTTP, factory, parse, identity or cancellation failure. Changing the explicit selector or replacing the configuration during the request prevents installation. Only successful validation installs the new token/bearer; the owned temporary RestClient is disposed and a borrowed HttpClient remains usable.

Native RefreshAuthorizationAsync keeps the existing refresh_token form contract. With a configured ID, the installed token must already belong to that organisation and carry a Scope UID. The refreshed token and fresh account are validated before installation, and refresh must retain the installed UID. An unset ID retains legacy refresh behavior. Credential authorization and context reads use native cancellation; cancellation while waiting, during token acquisition or during the context read does not install staged state.

The numeric OAuth organisation ID, customer number and TeamworkTenantId are different identifiers. An organisation need not expose a Teamwork tenant. The consuming DMS provider separately validates its explicitly expected Teamwork tenant and mapped DMS user identity; its mapped ID need not equal the Scope UID. Demo-tenant discovery, actor/role permissions and the actual scope/reversibility of administrative writes remain separate prerequisites. A selected organisation does not by itself authorize global user, license or workflow mutations.

Published 2026.10.13 low-level AuthorizationApi.TokenWithHttpInfo and native TokenAsyncWithHttpInfo already accept organisationId; their installation semantics/signatures remain unchanged. A DMS direct-token adapter can use that published package without requiring this optional facade addition. DMS issue137 owns form/cache/CI inputs and tenant guard behavior. No exact demo ID or credentials are provided by these source changes, no secrets are set, and no new dependency is imported into the frozen DMS release.
