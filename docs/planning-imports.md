# Project planning imports

`HumanResourcesApi.ImportProjectResources` and `ImportProjectRevenues` add POST `/projectresource/import` and `/projectrevenue/import`, each with six sync/async/HTTP-info/native cancellation forms. Existing generated methods, authorization/account selection and serializers are retained.

`ProjectResourceImportRequest` and `ProjectRevenueImportRequest` are complete copied JSON objects. Data selects an original Base64 CSV string; Resources/Revenues select a defensive JSON-array copy. Null typed setters omit fields; empty strings/arrays and explicit JSON null through inherited indexers remain explicit. The pinned schemas have no required properties or minimum record count. The SDK requires a nonnull request object and validates known JSON kinds/Int64 and Int32 widths without inventing a content minimum. The server validates Base64, CSV columns and usable records. The SDK does not read files, decode CSV, re-encode it or automatically choose a representation.

Both representations may be supplied unchanged. Manufacturer prose says data takes precedence, but the resource-import prose mistakenly calls the JSON alternative revenues while its schema names resources. This workflow uses the schema's resources key and documents that contradiction; it never moves, removes or chooses fields locally. Real precedence/CSV acceptance remain a live verification task.

Resource JSON rows support projectNumber, humanResourceId, date, days, extraDays, comment and fee. Revenue rows support revenueGroup, projectNumber, date, amount and comment. Fields are available through the inherited JSON object, including unknown future fields and explicit optional null. Records must be objects; known text fields remain strings, humanResourceId is Int64 and days/extraDays are Int32. Fee/amount must be finite JSON numbers and are sent without client rounding or guessed nonnegative restrictions. Typed request setters/getters copy arrays and nested objects; transport snapshots the full body before I/O.

The manufacturer says resource dates identify a month and any day is treated as the first of that month. Comment, extraDays and fee affect the entire resource rather than a single month; the server truncates the fee to two decimal places. Revenue dates are similarly normalized to the first of the month; revenueGroup can identify a product group or a manually added group. The SDK preserves original strings/decimal values and delegates these effects, catalog existence and Projekte (Bearbeiten) permissions to the server.

The success response has no declared schema. Complete JToken/raw JSON, HTTP status and response/content headers are retained; arrays, objects, null and future shapes are not reduced to a fabricated count. HTTP 200 means completed or partially completed import and may still contain record errors. Callers must inspect the actual result; there is no aggregate success claim or partial-failure replay. Original error factory exceptions/diagnostics are retained before JSON parsing. Result fractions use bounded .NET decimal precision and may round or underflow; raw JSON stays exact and date-like strings remain strings.

Native cancellation reaches HTTP I/O. Cancellation after sending does not establish which records were applied. No new import retry, date conversion, revenue computation or automatic follow-up is added. Isolated fake fixtures exercise every public form, original CSV/JSON/both/empty/null choices, copied snapshots, unknown records, exact numeric widths, errors/partial results/headers and pre/active cancellation. No server is contacted. Real CSV/JSON acceptance, precedence, resource-wide effects, month/fee handling and partial failures require a coordinated exclusive test window and exact owned planning-resource cleanup; full support remains deferred.
