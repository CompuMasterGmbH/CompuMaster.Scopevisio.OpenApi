# Explicit travel-position creation

`AccountingApi.CreateTravelExtraPosition`, `CreateTravelOvernightPosition` and `CreateTravelVehiclePosition` expose the pinned POST /travelentry/position/{extra,overnight,vehicle}/new operations, each with six sync/async/HTTP-info/native cancellation forms. Existing generated APIs, authorization and FileForm remain unchanged.

`TravelPositionCreationRequest` provides copied complete JSON plus travelEntryId, typeDisplay, amount, taxRate and fileform. Extra creation takes this base request. Overnight/vehicle creation take `TravelDistancePositionCreationRequest`, which adds the optional original numeric kilometres. The manufacturer reuses TravelentrypositionForm for overnight and vehicle and describes vehicle catalogs even for overnight. The SDK exposes the declared shared fields without inventing overnight categories or reimbursement calculations.

Required travelEntryId must be an Int64 JSON integer; zero/negative values remain server choices. Required fileform must be a JSON object array. Every supplied receipt requires a data string; optional filename is a string or JSON null. The schema has no minimum receipt count or data length, so explicit empty arrays/data strings are preserved. Optional fields may be omitted or explicitly JSON null. Known numbers must be finite; original values, rates and typeDisplay text are not locally range/enum/currency/scale validated. The server enforces current catalogs, rates, identity, amounts and distance semantics. Unknown fields remain complete, including nested receipt extensions.

`TravelReceiptRequest` copies complete receipt JSON and exposes the original filename/data strings. Typed null setters omit fields, while inherited indexers retain explicit optional JSON null. Receipt arrays are defensive copies and the full body snapshots before transport. The data is original Base64 text; server acceptance is authoritative. The client does not access local files, decode/re-encode content, truncate data, infer a MIME type or invent a size bound. When no filename is supplied the manufacturer assumes a PDF; the SDK does not fabricate a filename. Existing FileForm remains compatible.

The manufacturer declares HTTP 201 without a fixed success schema. Complete JToken/raw JSON/status/response+content headers retain all returned fields, including errors if present; no position ID or aggregate success is inferred from an absent field. Empty responses have null data and unspecified JSON shapes remain intact. The existing exception factory runs before JSON parsing, preserving original error content/custom exceptions. Parsed fractions use bounded .NET decimal precision and may round or underflow; raw JSON remains exact and date-like strings remain strings.

The documented profile is Reisekostenerfassung Belege (Anzeigen). HTTP 404 covers either a missing travel entry or authorization; the client preserves the original diagnostic without treating it as proof of either cause. No creation retry or follow-up is added. Native cancellation reaches active HTTP I/O; cancellation after sending does not establish whether creation/upload occurred.

Isolated fake tests reproduce the missing public workflows and cover all forms, exact fields/Base64/filenames, empty/null/unknown choices, required raw kinds/Int64 widths/finite numbers, copied receipts/snapshots, original 404/custom errors, complete response shapes/headers and pre/active cancellation. No actual travel entry or file is uploaded. Catalog/rate/receipt/profile acceptance and created-resource cleanup require an exclusive coordinated live window with exact owned resources. Full support remains deferred; publication/downstream adoption are separate.
