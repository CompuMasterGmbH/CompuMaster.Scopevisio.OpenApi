# Explicit posting corrections, cancellation and document-number updates

AccountingApi adds CorrectPostingXml (POST /correctpostings), CancelPosting (POST /posting/cancel), ImportPostingCorrections (POST /postings/correction) and UpdatePostingDocumentNumbers (PUT /postings/update), each with six sync/async/HTTP-info/native-cancellation forms. Existing generated Postings/PostingRow, posting methods, authentication and account-selection defaults remain unchanged.

All four request bodies are optional in the pinned manufacturer contract; null omits the body. If supplied, PostingCorrectionXmlRequest requires the original postingXml string, and PostingDocumentNumbersUpdateRequest requires the original documentNumber string. Empty strings remain server choices because no minimum length is specified. XML is not parsed, normalized or reassembled. All thirteen XML/cancellation fields are retained, including explicit VAT/batch/master-data/file/reference/payment choices. importMasterDataMode is an original string (current values CREATEORUPDATE/CREATEONLY); spelling and future values are preserved for server validation without choosing a mode. Buchen (Anzeigen), import validity and actual privileges remain server-enforced.

PostingCancellationRequest retains original documentNumber, Int64 pdeRowNumber and optional cancellationDate text. The server uses the row number only if the document number is not provided. The documented date format is dd.mm.yyyy; omission requests real cancellation on the original date. The client does not select an existing posting, parse date text, fall back after a failure or infer an effective date. Journal (Bearbeiten) is server-enforced. HTTP 200 can describe a performed or ignored cancellation with errors; 404 missing document and 409 already cancelled remain original failures, not successful idempotent results.

PostingCorrectionImportRequest preserves adjustVatKey, autoCreateTax and copied rows. Each supplied PostingCorrectionRowRequest requires Int64 postingDate, original documentNumber and account strings and finite amount. Its 24 declared fields include original Unix-millisecond dates, cancellation/document/account strings, finite currency/rate/discount values, Int64 periods, and copied PostingCorrectionDimensionRequest selections. No SKR03 sample accounts, current date/period, tax generation, VAT key, summary account, currency conversion or balancing is inserted. Zero, negative and tiny finite amounts remain unchanged. Supplied row/dimension entries must be objects with known compatible field kinds/widths; optional explicit null and unknown fields remain available. The schema has no root required fields or array minimum; omission/empty arrays are retained. The server requires at least two actual posting rows, valid chart-specific accounts, a summary account for personal accounts, balancing and appropriate Datenimport (Bearbeiten) privileges.

UpdatePostingDocumentNumbers retains the selected documentNumber and distinct optional externalDocumentNumber/internalDocumentNumber. The client performs no year/increment expansion, lookup or generated replacement; Buchen (Anzeigen) and existing posting identity remain server-enforced.

All six input models copy complete source objects; typed null setters omit properties and array setters/getters return defensive deep copies. A complete body snapshot is prepared before HTTP I/O. Required known fields and numeric JSON widths/finite kinds are checked without reconstructing financial state.

The correction-import response references PostingsNewResponse with Int32 status and string insertCount/updateCount; the SDK retains these original fields, future feedback and complete JSON without fabricating aggregate success. Other operations have no fixed success schema. All retain exact raw JSON/status/response+content headers and configured exception-factory errors. Date-like result strings stay strings. Parsed fractions use bounded .NET decimal precision and may round or underflow; raw JSON stays exact. No mutation retry or partial-failure replay is added. Native cancellation reaches HTTP I/O; cancellation after sending cannot prove which changes were applied.

Twelve missing-workflow smoke tests fail before the API addition. Isolated fake HTTP tests cover all forms, exact XML/cancellation/row choices, defaults and optional-body omission, required and known kinds/widths, finite amounts, all typed fields, snapshots, complete results/errors/headers and active/pre-cancellation. No real posting is imported, corrected, cancelled or renumbered. Exclusive coordinated live acceptance with owned fixtures and restoration/cleanup remains pending. Full support, publication and downstream package adoption are separate.
