# Complete outgoing-invoice update by original number

OutgoingInvoiceApi.UpdateOutgoingInvoice exposes POST /outgoinginvoice/{number} with six sync/async/HTTP-info/native-cancellation forms. The original document number is required and escaped as one path segment without trimming or numeric parsing. Blank numbers and relative dot segments fail before HTTP. Existing generated methods/models, authorization and account-selection defaults are preserved.

The manufacturer marks this endpoint BETA and requires Rechnungen (Bearbeiten). Already posted invoices are forbidden (HTTP 403). HTTP 404 covers both an absent invoice and missing write permission; the SDK preserves the original diagnostic without inferring existence or applying permission/state repair. Isolated success does not establish production suitability.

OutgoingInvoiceUpdateRequest provides all 49 writable fields of the 58-property OutgoingInvoiceForm. Nine read-only customer/account/name/number fields are derived by the server and have no new typed setters; complete source/raw indexer metadata remains intact, including known read-only kinds/widths when explicitly supplied. The composed OutgoingInvoiceWithPaymentTermForm/OutgoingInvoiceBaseForm fields are already included, so no duplicated or conflicting derived defaults are inserted.

The body is optional in the operation contract; null omits it. A supplied object must contain Int64 customerContactId and documentDate because the schema explicitly requires them. Creation-oriented prose nevertheless makes customerContactId conditional on project settings and describes an omitted current-date default for documentDate. Those conflicts are documented rather than resolved by choosing a customer, project, current date or substituting existing state. Exact partial-update/default behavior needs live acceptance.

Original document/account/project/contact IDs, strings, Unix-millisecond dates, locale/currency/exchange-rate/reference/tax-country selections, permissions, text/address/shipping/intercompany choices and finite amount/discount values are retained. Explicit false/zero/empty values remain distinct from omission and optional explicit JSON null. No address/permission enumeration beyond declared Int64 width is guessed from examples, no sample/year/increment number is generated, and no contact-derived language/currency/payment type is inserted. Original enum strings and future server values remain server-validated.

The server owns project/zone mandatory settings, current customer-derived values, user-contact identity, address/permission/profile interpretation, currency/exchange-rate availability and invoice state. Payment/discount prose describes creation-time fallback to the customer's personal account, discount amount versus percent exclusion, date ordering and dependent fields. The SDK retains explicit caller choices without reconstructing invoice state, calculating discounts or assuming omitted update fields retain current permissions. EndDiscount remains an original amount/percentage selected by isEndDiscountAbsolute.

OutgoingInvoiceUpdatePositionsRequest requires a positions array when supplied; each OutgoingInvoiceUpdatePositionRequest requires name by the schema, even though prose makes name mandatory only for headings/free text. All 27 position fields preserve original product/type/account/VAT/dimension strings, dates, quantities, discounts and net/gross price choices. No minimum array count, product lookup or amount calculation is added. copyProductsToPositions is explicit; the manufacturer says product defaults apply only to values not provided by the caller. typeDisplay fallback to Produkt is server behavior and is not applied locally. Exact position replacement/update semantics remain part of beta live acceptance.

OutgoingInvoiceUpdateCustomFieldRequest requires a customFieldName string and the presence of customFieldValue. The latter's schema declares object while its example is a string; the SDK retains complete original JSON, including explicit null, without coercing to an object or guessing a custom-field type. Actual custom-field names, valid types and removal semantics remain server-authoritative.

All four models copy complete source JSON. Typed null setters omit properties; raw indexers preserve unknown fields and optional explicit JSON null. Nested array/object/JSON getters and setters are defensive copies, and the complete transport body snapshots before HTTP I/O. Known required kinds and finite numeric/Int64 widths are checked without fetching current state.

The success response has no fixed JSON schema. Complete JToken results, exact raw JSON, status and response/content headers remain accessible; configured exception-factory errors run before parsing. Empty bodies have null data and future shapes remain intact. Date-like strings remain strings; parsed fractions use bounded .NET decimal precision and may round or underflow, while raw JSON remains exact. No mutation retry or partial-failure replay is added. Native cancellation reaches actual HTTP I/O; cancellation after sending cannot establish the invoice outcome.

Three missing-workflow cases fail before implementation. Isolated fake HTTP fixtures cover all forms, original escaped selection, all writable field mappings and nested shapes, required schema fields, known kinds/widths/nonfinite values, copied metadata, complete results/errors/headers and active/pre-cancellation. No real outgoing invoice is updated or posted. Beta customer/project/positions/payment/permissions acceptance requires an exclusive coordinated live window, owned fixtures and verified restoration/cleanup. Full support, release and downstream adoption remain pending.
