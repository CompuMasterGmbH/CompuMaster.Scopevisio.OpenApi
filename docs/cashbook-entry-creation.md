# Explicit cashbook entry creation

Additive `CashbookApi.CreateCashbookEntryWithResult` provides six sync/HTTP-info/async/native-cancellation forms for POST `/cashbookentry/new`. The existing `CreateCashbookEntry(CashbookEntryForm)` signatures, historical zero amounts and null-data behavior remain unchanged. The distinct method name preserves existing calls with a null legacy body.

`CashbookEntryCreationRequest` and `CashbookEntryDimensionRequest` are extensible JSON objects. Constructors deep-copy complete source objects; typed null setters omit fields and inherited indexers retain unknown fields and optional explicit JSON null. Assigned/returned dimension arrays are defensive copies. Complete request JSON is cloned, validated and serialized before HTTP admission.

The current schema requires cashbookId and documentDate as full signed Int64 JSON integers. Explicit zero, negative and full-range values are forwarded unchanged because no range constraints are declared; actual cashbook/date validity remains server-authoritative. Document timestamps remain Unix epoch milliseconds. The example extension mentions a first-day-of-month timestamp, but this does not authorize converting caller values. Optional receipt/expense amounts have no declared sign/nonzero/range rule; unset amounts stay absent and explicit zeros or negatives remain unchanged. Optional account numbers, external number, free text and notice are not normalized or looked up. Nonfinite numbers anywhere in the request are rejected because they are not JSON numbers.

The response-only internalDocumentNumber cannot be supplied, including explicit null. Non-null known optional strings/numbers/arrays must have their declared kinds. Each supplied dimension object requires full Int64 dimensionNumber/dimensionEntryNumber. An optional explicit dimensionEntryName can cause the server to create a missing entry; its documented missing-name default is the dimension number. The SDK does not add a name, look up dimensions or choose creation policy. Empty dimension arrays remain explicit.

The copied request prose says topic is required, although neither the referenced schema nor historical form defines it. Validation follows the declared cashbookId/documentDate requirement and does not invent topic. The server requires Kassenbewegung eingeben (Bearbeiten). The pinned HTTP 201 declares no response schema; complete JToken/raw JSON/status/combined headers remain available without fabricating an identifier or resource model. Date strings remain text; parsed fractions use bounded .NET decimal precision/range while RawJsonContent is exact. Original factory/errors remain authoritative before parsing; no uncertain write is automatically retried. Native cancellation reaches active HTTP I/O and does not prove that a submitted creation had no server effect.

136 isolated fake-host cases cover all forms, omitted/explicit values, full Int64/zero/nested selections, original future fields, read-only and kind/width validation, nonfinite numbers, copied pre-admission bodies, complete/empty/null/scalar 201 results, malformed/overflow JSON, original factories/errors, disabled-factory error results, pre/active cancellation and legacy zero/null-data/token behavior. Before implementation, 116 missing-workflow/request failures were reproduced while the legacy regression passed. Actual financial/profile/dimension behavior remains untested; a resettable account and newly coordinated exclusive acceptance window are required. Full serialized matrix, publication and downstream adoption remain separate parent #17/DMS #90 prerequisites. No actual cashbook entry was created during this work.
