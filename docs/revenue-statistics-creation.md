# Product revenue-account and statistics creation

`AccountingApi.CreateProductRevenueAccounts` and `CreateStatisticsPostings` expose POST /revenueaccounts/new and /statisticspostings/new, each with six sync/async/HTTP-info/native cancellation forms. Both require a JSON object body. Their root schemas require no individual fields or minimum entry count, so supplied empty objects/arrays and optional explicit JSON null are preserved.

Copied extensible input models provide the declared shapes: ProductRevenueAccountsCreationRequest, ProductRevenueAccountEntryRequest, ProductRevenueAccountAssignmentRequest, StatisticsPostingsCreationRequest and StatisticsPostingEntryRequest. Typed null setters omit fields, inherited indexers retain unknown fields and optional explicit JSON null, and arrays/source objects are defensive deep copies. The complete body snapshots before HTTP I/O.

Each supplied product entry requires an original productNumber string; each supplied non-default account assignment requires an original accountNumber string. Empty text remains unchanged because no schema minimum length is given; the server validates usable identities. Optional taxCase, Int64 taxCaseId, countryIsoCode and original validFrom/validTo date strings are preserved. The date schema pattern/example uses yyyy-MM-dd while the prose also says dd.MM.yyyy. The client does not choose a conflicting format or infer year boundaries/order.

useDefaultAccounts is a string, not a JSON boolean: current enum values are true/false/inherit, while the prose also says INHERIT. Original caller spelling is sent without case conversion or a restrictive enum that rejects future server choices. The manufacturer states enabling defaults does not delete non-default assignments; no account deletion or automatic fallback selection is added. Produktverwaltung (Bearbeiten), products/chart membership and actual assignments remain server-authoritative.

The revenue response references MaterialResponse with status/results/feedback and copied purchase-order wording. The SDK preserves complete JSON and feedback without fabricating a purchase order, matching a fixed generated purchase-order type or declaring aggregate success. ErrorRecord locationIdentifier is declared object but examples use an integer; the original JSON remains available without coercion. Callers inspect actual status/results/feedback, including future severities and fields; live clarification remains outstanding.

Each supplied statistics row requires an Int64 date, original accountNumber string and finite nonzero numeric amount. Negative quantities are preserved. The zero check examines the original JSON number's mantissa rather than converting to decimal, so tiny finite values such as 1e-100 are not misclassified as zero by decimal underflow. Known text/zone fields and optional Int64 dimension_1 through dimension_10 are validated by kind/width. Zone requirements depend on server settings, and accounts/dimensions/date semantics remain server decisions. The client does not normalize timestamps or quantities.

AutoCreateAccount is an explicit nullable boolean; omission never enables automatic account creation in the client. AutoAccountDecimal is the original optional Int64 decimal-digit selection with server range validation. Statistikbuchungen (Bearbeiten) remains server-enforced. The manufacturer declares HTTP 200 for all postings and 201 for a posting; raw status/content remain distinct without inferred count/completeness.

Complete JToken/raw JSON/status/response+content headers and original exception-factory errors are retained. Empty bodies have null data and unknown result shapes remain accessible. Date-like result strings remain strings; parsed fractions use bounded .NET decimal precision and may round or underflow, while raw JSON remains exact. No new mutation retry, partial replay, account lookup, local chart merge or follow-up occurs. Native cancellation reaches actual HTTP I/O; cancellation after sending cannot establish which records were applied.

Isolated fake fixtures reproduce missing workflows and cover all forms, exact nested fields/default/date choices, explicit auto-account options, known required kinds/widths, zero/nonfinite/tiny amounts, dimension fields, deep snapshots, complete feedback/results/status/errors/headers and active/pre-cancellation. No product accounts or statistics are created on a real server. Real owned product/account/statistics/profile/zone/feedback acceptance requires exclusive coordinated access and verified cleanup/restoration; full support remains deferred. Publication/downstream adoption are separate.
