# Explicit account-mapping mutations

`AccountingApi.CreateAccountMapping`, `UpdateAccountMappingEntry` and `DeleteAccountMapping` add POST accountmapping, PUT accountmapping/entry/id and DELETE accountmapping/id. Each has six sync/async/HTTP-info/native cancellation forms. Existing account-mapping reads, generated APIs, obsolete annotations, authorization and serializers remain unchanged.

The creation and update request bodies are optional in the pinned OpenAPI contract. Null omits the body; a supplied object must satisfy its schema-required fields. Creation requires a description string; entry update and supplied nested creation entries require accountScope/accountExternal strings. The schema supplies no string length/minimum constraint, so empty text remains unchanged for server validation. No fictitious blank body or empty-object creation is inserted. The server reports unusable missing data.

`AccountMappingCreationRequest` copies complete JSON and exposes all twelve form fields: description, accountingArea, includePersonalAccounts, validFrom, validTill, accountFormat, glAccountLengthFrom, glAccountLengthTo, personalAccountLengthFrom, personalAccountLengthTo, accountType and entries. `AccountMappingEntryUpdateRequest` exposes the original two account strings. Typed null setters omit fields; optional explicit JSON null remains representable through inherited indexers. Arrays/nested objects are defensive copies. The complete request snapshots before HTTP I/O. Known raw text/boolean/Int64 kinds are validated without coercion, guessed ranges, timestamp conversion or account-length interpretation; negative/zero values remain server choices.

Omitted accountingArea retains the manufacturer's active-accounting-area choice. No undocumented includePersonalAccounts default is imposed. Account numbers retain leading zeros and original spelling. The accountScope/accountExternal naming and description can be counterintuitive: the client keeps the exact wire names without interpreting mapping direction from the English names. The server checks chart membership, formats and account types. Entry id/modifiedTs are described as response-only; typed inputs do not populate them. Complete caller-supplied raw JSON is retained with Int64 validation for these known keys, without inferring path identity from the body or silently removing fields.

The server enforces Stammdaten (Bearbeiten). Creation declares HTTP 201 and may return 409 for an existing mapping or 404 for an unavailable area; entry update and deletion declare HTTP 200. No fixed success schemas are supplied. JToken/raw JSON, status and response/content headers retain any complete JSON result; empty responses have null data. Original diagnostics and custom exception factory exceptions run before JSON parsing. Result fractions use bounded .NET decimal precision and may round or underflow; raw JSON remains exact and date-like strings stay strings.

Deletion always targets the caller-selected Int64 mapping ID and deletes all its entries. The SDK does not choose the active mapping, perform list/deletion sweeps or infer completion from fabricated row counts. Path IDs use invariant original Int64 text. There is no new mutation retry, automatic chart repair or follow-up request. Cancellation reaches active HTTP I/O and cannot establish whether the server already applied the operation.

Isolated fake fixtures reproduce the absent workflows and test all public forms, optional-body omission, required/raw/nested kinds, original account strings, numeric widths/default omission/false/null/empty choices, copied snapshots, undeclared result shapes, raw headers/error factories and active/pre-cancellation. No accounting server is contacted. Real creation, selected-entry update, profile/conflict behavior and deletion of exact owned mappings require an exclusive coordinated window and cleanup. All operations remain deferred for full/live support; publication and downstream adoption are separate.
