# Explicit open-item mutations

AccountingApi exposes ClearCreditorOpenItems, ClearDebtorOpenItems, RebookCreditorOpenItems, RebookDebtorOpenItems and SetOpenItemReminderLevels. Each has six synchronous/asynchronous/HTTP-info/native-cancellation forms using the five documented POST routes. Existing read/search APIs and authorization/account selection remain unchanged.

All five operations require an object body. OpenItemClearingRequest, OpenItemClearingGroupRequest and OpenItemClearingDocumentRequest preserve explicitly selected groups/documents and original optional document-number strings and clearing amounts. Their schemas specify no required individual properties or minimum array count. Empty objects/arrays and optional explicit JSON null are preserved. Finite amounts are neither rounded nor clamped; zero and negative amounts remain server choices. Journal (Bearbeiten), actual documents and clearing validity remain server-enforced.

OpenItemRebookRequest preserves documentNumber, postingDate, postingPeriod, sourceNumber and targetNumber as original strings. Leading zeroes and special-period text are not converted to numbers. The contract has concrete defaults such as document 2025-000012, date 31.12.2025, period 13 and accounts 10002/10001. The client never inserts these values, chooses an existing item/account, fetches current state or interprets an omitted field as a verified server action. The manufacturer declares Debitoren (Anzeigen) for both creditor and debtor rebooking; the unusual creditor declaration needs live clarification. Actual privileges, dates/periods and account identity remain server-authoritative.

OpenItemReminderLevelsRequest requires an openItems array without a schema minimum count. Each OpenItemReminderLevelRequest requires a documentNumber string and an Int32 reminderLevel. Empty strings and the full Int32 range are passed unchanged because no narrower schema constraint is given; the server validates actual documents and available reminder levels in the accounting area. Journal (Anzeigen) remains server-enforced. HTTP 200 means the items were processed individually; callers must inspect each result for success or failure. No aggregate success or transactionality is inferred. HTTP 404 can mean no accounting area, and original server errors remain accessible.

All models deeply copy complete source JSON. Typed null setters omit fields; raw indexers preserve unknown fields and optional explicit JSON null. Array setters/getters return defensive copies, and complete transport bodies are snapshotted before HTTP I/O. Known JSON kinds, required fields and integer widths are checked before sending without guessing undocumented business constraints.

The manufacturer defines no fixed success JSON schema for these operations. Complete JToken results, exact raw JSON, status and response/content headers remain available, including item failures and future fields. Empty response bodies have null data. The configured exception factory runs before parsing, preserving original failures. Parsed fractions use bounded .NET decimal precision and can round or underflow; raw JSON remains exact. No new mutation retry or partial-failure replay is added. Native cancellation reaches HTTP I/O; cancellation after sending cannot establish which changes occurred.

Fifteen missing-workflow smoke tests fail without the additive API partial. Isolated fake HTTP tests cover every form, exact choices/default omissions, required and optional nested shapes, amount/Int32 boundaries, partial feedback, deep copies, original errors/headers and active/pre-cancellation. No actual open items, postings, accounts or reminder levels are changed. Live acceptance needs a coordinated exclusive server window, verified owned fixtures and complete cleanup/restoration. Full support, publication and downstream adoption remain separate.
