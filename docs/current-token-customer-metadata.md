# Current token customer metadata

The handwritten `TokenResponse` partial adds optional `CustomerId` (`customerId`) and `PublicId` (`publicId`) string properties from the current ten-field manufacturer schema. All seven required token fields, existing constructor/signatures/defaults/validation and historical generated members are retained. Strings remain original, including leading zeros, whitespace and empty text. Missing or explicit null metadata becomes null; normal JSON and data-contract serialization omits null optional values.

The numeric Scope organisation ID, organisation name, user UID, opaque Teamwork tenant ID, customer/tenant string identifier and public customer-number string are distinct namespaces. These optional values are metadata; neither selects an account nor establishes organisation/user/Teamwork binding or permissions. No lookup, GUID/numeric conversion, authentication/token/context/configuration/cache change is added. The staged explicit organisation and fresh-account guard remains byte-identical.

JSON serialization (`ToJson` included) supplies these known metadata fields. The preserved generated equality/hash and diagnostic `ToString` continue considering their original fields only; they do not establish full token equality or include the new metadata. They must not be used as tenant identity proof. Adding optional read metadata does not change historical constructor requirements or serialization of tokens without it.

Isolated fixtures cover current field names/kinds/optional state, original strings, JSON and data-contract roundtrips, legacy behavior and explicit fake-host organisation/fresh-account acceptance/rejection. Actual metadata/identity remains unverified and requires a new finite exclusive Demo window with exact numeric Scope organisation, fresh account and distinct opaque Teamwork tenant proof, without PROD fallback or historical grants. Source validation is separate from SDK publication and DMS adoption.
