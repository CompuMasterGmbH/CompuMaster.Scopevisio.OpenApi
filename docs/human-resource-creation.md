# Human resource creation

`HumanResourcesApi.CreateHumanResource` and five related synchronous/asynchronous/HTTP-info/native-cancellation forms add POST `/humanresource/new` from the pinned contract. Existing generated APIs, obsolete annotations, authorization and default configuration remain unchanged.

`HumanResourceCreationRequest` copies complete JSON and exposes contactId, role, position, department, projectBox, topic, location, fee, validFrom, validTill and allowMultiple. Required contactId must be an Int64 JSON integer; identifiers of either sign and zero are left for server validation. Required planning values must be nonblank original JSON strings. Known optional kinds are checked before I/O, including finite numeric fees; unknown fields and optional explicit JSON null remain available through the inherited object. Typed null setters omit fields. The request is deeply copied, validated and serialized before transport; subsequent caller changes cannot change the captured body.

The manufacturer schema requires contactId/validFrom/validTill but its operation prose describes generating the calendar only when both planning bounds are supplied. This workflow follows the schema's required fields. The planning schema pattern and example use yyyy-MM-dd while the same descriptions also say dd.MM.yyyy. The SDK preserves the original supplied strings, including month boundaries, rather than choosing a conflicting format or converting dates. The server decides acceptance and date ordering. Catalog strings remain original; no enum prevents tenant-specific or future catalog values. Fees remain caller-selected without invented nonnegative restrictions or rounding. Omitted allowMultiple retains the documented server default false; true is an explicit request for multiple resources for the same contact.

The server enforces Human-Ressourcen Verwaltung (Bearbeiten), contact visibility/existence, catalogs, planning semantics and duplicate handling. `HumanResourceCreationResponse` copies all JSON and exposes nullable status/humanResourceId/location plus complete errors. Inspect errors even when HTTP status is 201; the SDK does not infer successful workday generation or auto-retry. Omitted or JSON-null response fields remain distinguishable through inherited JSON; empty/JSON-null bodies yield null data. Unknown fields, exact raw JSON, HTTP status and response/content headers are retained. Response fractions use bounded .NET decimal precision and may round or underflow; raw JSON stays exact. Date-like response strings remain strings.

Native cancellation reaches actual HTTP I/O. Cancellation after sending cannot establish whether creation occurred. The SDK adds no creation retry, date repair, follow-up request or permission inference. The existing exception factory runs before JSON parsing and preserves original server diagnostics/custom exceptions.

Isolated fake HTTP tests reproduce the absent API and cover all public forms, original dates/identifiers, explicit false versus omission/null, unknown data and copied snapshots, invalid known raw types, finite fees, 201 error details, empty/future results, headers, original errors and active/pre-cancellation. No real resource is created. Live date acceptance, catalog/profile permissions and returned resource/errors require an exclusive coordinated test window and exact owned-resource cleanup; full support remains deferred.
